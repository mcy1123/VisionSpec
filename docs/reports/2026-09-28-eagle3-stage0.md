## 1. 数据与划分（已核验）

阶段 0 最重要的一件事是**证明 EAGLE-3 与 GLANCE 用的是同一批行**。已从原始 parquet 逐条核验：

```
pool_499.parquet        499 行 = 439 train + 60 heldout
  └ train 439 = video_opd_train_409.parquet (409)  ∪  video_heldout_30.parquet (30)
  └ heldout 60 ⊇ video_fresh30.parquet (30, 用于 SFT 选点)
```

| 划分 | 行数 | 用途 | 与 GLANCE 的关系 |
|---|---|---|---|
| **train** | 409 | EAGLE-3 训练 | 与 GLANCE OPD **完全相同**的训练行 |
| **select** | 60 | EAGLE-3 选 checkpoint | GLANCE 选点用的同一批（`pool_499` 的 heldout） |
| **holdout30** | 30 | 最终对比 | GLANCE 的独立留出，**从未参与任何选点** |

三项**两两互斥**（脚本内 `assert`，非人工检查）。`holdout30` 位于 pool 的 **train** 划分内——
这正是「从未参与选点」的定义；若不成立脚本会直接报错，而不是把乐观数字报出来。

### 生成物

| 文件 | 内容 |
|---|---|
| `/mnt/local/mcy/GLANCE/data/eagle3_train.jsonl` | 409 行，`id` + `conversations`，assistant = **target greedy 输出**（非数据集标注） |
| `/mnt/local/mcy/GLANCE/data/eagle3_select.jsonl` | 60 行 |
| `/mnt/local/mcy/GLANCE/data/eagle3_holdout30.jsonl` | 30 行 |
| `/mnt/local/mcy/GLANCE/data/eagle3_manifest.json` | 逐行 `prompt_len`/`seq_len`/`ended_with_eos`/`roundtrip`，捕获阶段据此定位 loss mask |

### 全量往返门禁（499/499 逐 token 比对，非抽样）

```
train:     checked=409 identical=0 template+1=401 template+2=5 retokenised=3 bad=0
select:    checked= 60 identical=0 template+1= 59 template+2=1 retokenised=0 bad=0
holdout30: checked= 30 identical=0 template+1= 30 template+2=0 retokenised=0 bad=0
```

三类结果**全部有解释、无静默**：

1. **`template+1`（490 行）**：Qwen 模板在 assistant `<|im_end|>` 后补一个 `\n`。
2. **`template+2`（6 行）**：这 6 条 rollout 撞到 token 上限、**没有 EOS**，模板补上缺失的
   `<|im_end|>` 再加 `\n`。这解释了为什么不能简单按 `seq_len` 截断。
3. **`retokenised`（3 行）**：Qwen 的 BPE **不是单射**——`ĠLang|uell`（rollout）与
   `ĠL|angu|ell`（重新编码）是同一个字符串的两种合法切分。已对全部 499 行验证
   `decode(re-encode(text)) == text` 成立，即**文本忠实，只是切分不同**。

**由第 3 点得出的设计决定**：JSONL 只承载文本，无法保证逐 id 还原。所以
`capture_features.py` **不**从 JSONL 重新编码后训练，而是把整段对话经**同一个 processor**
渲染后做**一次** teacher-forced forward，ids / hidden states / loss mask 全部来自这一次前向
——三者按构造自洽，标签不可能与教师状态错位。

## 2. SpecForge 能做什么、不能做什么（本阶段最关键的发现）

原计划用 AngelSlim / SpecForge。实测结论：**SpecForge 没有任何多模态通路**，
但它的**离线训练器可以吃手写的特征文件**——这才是可用的接缝。

### 2.1 三个「静默失败」的坑（都会让结论反向而不报错）

| 坑 | 证据 | 后果 |
|---|---|---|
| `target_model_type` 是**死字段** | 全仓库仅 3 处出现，全在 JSON，**零个 Python 消费者** | 配了也没用；真正的门是 `model.input_modality`，EAGLE3 只注册 `("offline","text")` |
| **无多模态通路** | `pixel_values`/`image_grid_thw` 仅存在于 `inference/media.py`（死代码，零导入）；`OnlineEagle3Model.forward` 无 `**kwargs`（有测试锁死）；内置 capture 强制 `ForwardMode.DECODE`，而 SGLang 的多模态分支**要求非 decode** | 即使注入 media 也只会得到**文本隐状态**；故必须自己写捕获 |
| **mRoPE 会静默失效** | `_init_rope` 先读 `rope_type`；Qwen3-VL 实际配置是 `rope_type: "default"` + `mrope_section` + `mrope_interleaved: true` | 命中 `"default"` 早返回，装成 **1D RoPE**，不报错 |

另外两个配置陷阱（已避开，见 §2.3）：

- `embed_tokens` 在 Qwen3-VL 里是 **`model.language_model.embed_tokens.weight`**（文本塔嵌套），
  不是 SpecForge 默认的 `model.embed_tokens.weight`；
- SpecForge 只实现了 **chunked**（Qwen2.5-VL）mRoPE，Qwen3-VL 用的是 **interleaved**。
  喂错布局**不报错**，只是旋转错、接受率变差。

### 2.2 我们打的补丁（可回滚、可验证）

`repro/eagle3/specforge_patches.py`，作用于 `/home/mcy/Projects/SpecForge`：

| # | 文件 | 改动 |
|---|---|---|
| 1 | `runtime/data_plane/offline_reader.py` | `_OFFLINE_EAGLE3_KEYS` 加入 `position_ids`（否则特征被静默丢弃） |
| 2 | `algorithms/eagle3/data.py` | `normalize_offline_sample` 输出 3 轴 `position_ids` |
| 3 | `modeling/draft/llama3_eagle.py` | 新增 `_mrope_interleaved_axis_index` / `_select_mrope_axes`，`apply_multimodal_rotary_pos_emb` 支持 interleaved |
| 4 | 同上 | `_init_rope`：声明了 `mrope_section` 时优先 mrope；缺 `mrope_interleaved` 则**报错而非猜** |
| 5 | 同上 | 4 个 attention 调用点串上 `mrope_interleaved` 标志 |

改动量：**3 文件 / +84 −10 行**。原文件备份在同目录 `*.eagle3qwen3vl.orig`，
`python specforge_patches.py --revert` 可完全还原。

### 2.3 验证结果（全部零 GPU、CPU 完成）

**(a) interleaved mRoPE 与 transformers 数值等价 —— 带否定对照**

```
case                                  max|diff|     relative
patched interleaved vs transformers    0.000e+00    0.000e+00
unpatched chunked vs transformers     5.542e+00    1.249e+00
PASS: interleaved matches to 0.000e+00
```

补丁**逐位等于** transformers 的 `Qwen3VLTextRotaryEmbedding`。否定对照（未打补丁的
chunked 路径）偏差达量级的 125%，说明**这个测试真的能测出它要测的 bug**——
一个恒过的测试等于没有测试。

**(b) 配置 vs SpecForge schema + 注册表 + target 权重键**

```
schema: OK (6 top-level keys)     registry: OK (mode=offline, strategy=eagle3, attention_backend=sdpa)
draft params: fc 50.3M + attn 41.9M + mlp 151.0M + head 131.1M = 0.374B
embedding_key: model.language_model.embed_tokens.weight -> model-00001-of-00004.safetensors
lm_head_key:   lm_head.weight                            -> model-00004-of-00004.safetensors
PASS
```

`0.374B` 与计划里「~0.40B」一致（草稿词表 32000）。target 的 `model.safetensors.index.json`
**存在**，且两个键都在——这清掉了一个原本可能致命的阻塞（`TargetHead.load_weights` 硬依赖 index）。

**(c) 读入 → normalize → collate 端到端（真实 `.ckpt`，形状真实）**

```
_OFFLINE_EAGLE3_KEYS = ('input_ids','loss_mask','hidden_state','aux_hidden_state','position_ids')
position_ids (3, 1, 1237) -> collated (3, 4, 1253)
hidden_state (4, 1253, 12288) = 3 x target width 4096
PASS
```

这条最要紧：补丁 1、2 **都会静默失败**（特征被丢弃 / 张量进不了 forward），
静态检查看不出来，所以必须跑通真实管线。已跑通。

## 3. loss mask 的口径（一个容易错一位的地方）

按 SpecForge `parse.py` 的语义：**从 assistant 第一个内容 token 到收尾 `<|im_end|>`（含）**。
本文的捕获把整段序列按**完整渲染长度**存储（**不**截断到 `seq_len`），于是模板补的那个 `\n`
正好落在最后一个下标，`normalize_offline_sample` 的 `loss_mask[0,-1]=0` 清掉的是这个
**无监督目标**的换行，而不是吃掉一个真标签。

若按 `seq_len` 截断，最后一位会是一个**真被监督的 token**，被静默清零，且与 SpecForge
自己的 parser 不一致。这是阶段 0 修正掉的一个设计错误。

## 4. 训练配方（用 EAGLE-3 推荐配方，不为追 GLANCE 调参）

`repro/eagle3/run_eagle3_video.yaml`：

| 项 | 值 | 说明 |
|---|---|---|
| 草稿层数 | 1 | EAGLE-3 固定 |
| `ttt_length`（= draft-len） | **3** | 与推理解码深度一致 |
| `learning_rate` | 1e-4 | EAGLE-3 参考值 |
| aux 层 | **[1, 17, 32]** | EAGLE-3 默认 `[1, n//2-1, n-4]`，**刻意不用** GLANCE 的 5 层 |
| 输出 | draft_vocab 32000 + 词表映射 | EAGLE-3 标准，复现 ~0.4B |
| `attention_backend` | sdpa | 支持 mRoPE、不依赖 flex 内核 |
| epochs | 40 | 每 250 步存点 |

**不收敛时的修复序列**（对应计划里的修复 1–5，已落成具体开关）：

```bash
TTT=7  ROUND=2 GPU=7 bash 20_train.sh     # 修复1：ttt_length 3→7（推理时自回归误差更鲁棒）
LR=5e-5 ROUND=3 GPU=7 bash 20_train.sh    # 修复2a
LR=2e-4 ROUND=4 GPU=7 bash 20_train.sh    # 修复2b
ATTN=flex_attention ROUND=5 GPU=7 bash 20_train.sh   # 修复4：换注意力后端
```

修复 3（训练/推理 draft-len 一致）是**默认已满足**的约束，不是可调项：
`ttt_length` 与评测链式深度必须相同，评测脚本会断言。修复 5（官方预训练权重零样本）
只在训练确实失败时启用，且**必须标注为零样本**。

## 6. 尚未验证的部分（明确列出）

阶段 0 只覆盖到「特征能吃进去」。以下**没有**验证，不能当成已知：

1. **真实捕获未跑**。特征张量目前只用 stub 验证过形状与通路；真实 forward 的
   数值、单条耗时、显存峰值都还是估计（按 GLANCE 视频训练的经验估 ~1–2 s/行）。
2. **训练一步都没跑**。§2.3 证明了补丁正确、配置合法、数据可读，但
   `specforge train` 的端到端仍需一次真实运行。**风险点**：`TargetHead` 从
   分片权重读 `lm_head`/`embed_tokens` 的实际加载，以及 `draft_vocab` 词表映射的生成。
3. **评测框架未写**。这是**有意延后**：EAGLE-3 的链式验证器要在有 checkpoint 之后写，
   否则是无法测试的代码。计划见 §7。
4. **容器 GPU 未实测**。已验证挂载方案（target/venv/特征三者互相可见），但
   `--gpus` 与容器内可见的卡号（`sf` 容器只映射了 1、7 号）需在开训时确认一次。
5. **`sf` 容器没有 `/glance` 挂载**，也未装 sglang——它只适合当离线训练器。
   因此 `20_train.sh` 会另建 `sf-glance`。

### 6.1 异常记录：`sf` 容器在验证期间重启过一次

**现象**：`docker ps` 起初显示 `sf` 已运行 12 天；验证期间它重启了一次
（`RestartCount=1`，`StartedAt=2026-09-28T15:37:08Z`），因为策略是 `always` 所以自愈。

**已排除的原因**：容器**无内存上限**（`Memory=0`）、`OomKilled=false`、`ExitCode=0`
——即 PID 1 是被外部信号正常终止的，不是被 OOM 杀掉。宿主内存 503 GB、可用 256 GB，
`dmesg` 无 OOM 记录。

**我没有执行过** `docker stop/restart`，只用了 `docker exec`。

**可复现性**：把与重启同一秒运行的那条命令（`test_offline_ingest.py`）连跑 3 次，
3/3 通过，`RestartCount` 保持 1 —— **不可复现**。这台机器是多用户共享的，
最可能是外部操作。记录在此是因为训练要跑在容器里，这个现象值得保留在案。

**影响**：无。重启后所有门禁重跑通过。

## 7. 评测计划（阶段 2/3，待 checkpoint）

τ 的对比是**公平**的：同 target、同数据、同留出行，τ 直接可比；跨框架加速比不是严格公平比较，
会单独标注。计划：

- **同一把尺子**：把 EAGLE-3 草稿接进 GLANCE 的 `eval_video_opd.py` 逐行机制，
  复用同一 tokenizer / target / 留出 30 行 / 计时窗口。这样 τ 的差异只来自草稿头，
  不来自两套评测脚手架——比计划里「各用各的框架」更强。
- EAGLE-3 用**链式验证 depth=3**（与训练 `ttt_length` 一致，脚本断言），GLANCE 用 b63k8 树。
- `max_new_tokens=1024`、逐条交错、fp32、逐 token 与 target 贪心比对（无损门禁）。
- 报：τ 中位、E[a]、单条耗时、端到端加速比、无损条数；再按视频时长分桶看 τ 衰减。
- **选点只用 `select/`（60 行）**，`holdout30/` 在最终评测前一次都不碰。

论文对照基线：EAGLE-3 head (~0.40B, depth-3) 平均 τ ≈ 1.6 / 加速 1.15×；
GLANCE (budget-63, ~1.05B) τ ≈ 4.9。若本域 EAGLE-3 τ 落在 1.5–2.5，
说明视频域没有改变 EAGLE-3 的结构性劣势。

## 9. 结论（阶段 0）

1. **数据这一侧没有悬念**：EAGLE-3 与 GLANCE 用同一批 409 训练行、同一批 30 留出行，
   互斥关系由脚本断言而非人工确认；JSONL 已生成并通过 499 行全量往返门禁。
2. **SpecForge 走 VLM 这条路，官方是不通的**，但**离线训练器可以吃外部特征**，
   这条路已经打通并且**在 CPU 上验证到 collate 为止**。
3. **最容易出错、且错了不报错的那一处（interleaved mRoPE）已被证明与 transformers 逐位相等**，
   并有否定对照保证测试有效。
4. **剩下的全部是 GPU 工作**：真实捕获 → 训练 → 评测。阻塞条件是**排期**，不是显存，也不是方法。
