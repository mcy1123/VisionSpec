## 1. 数据集与固定评测设计

优先评估以下三个来源，并先核实官方下载说明、视频/标注是否可访问、许可、split 定义和题目格式；不得臆造路径、标签、视频或官方下载链接。

2. **MSRVTT-QA**：第二优先，内容更丰富的短视频 QA。

## 2. 两种回答格式：短问答与短解释必须分开评

请为每条 QA 固定两种输入模板（所有三臂使用相同视频、问题、模板、推理设置）：

**Format A：原始简短答案**
- 保留问题和必要选项，要求“直接简短回答，不额外解释”。
- 用于测题目正确性、target 熵、草稿 top-8、首个预测 token 的覆盖；可以测 τ，但如果答案只有一两个 token，必须明确**此模式不适合作为核心解码加速证据**。

**Format B：短答案 + 简洁视频依据**
- 统一提示“请先直接回答问题，然后用 1–2 句简短说明视频中可见的依据；无法由视频确认时请说明不能确认，不要编造细节”。
- 此模式用于获得适度长的自然生成，观察完整解码接受长度及速度，但**不得插入标准答案、参考 caption、隐含推理链或虚构证据**，不得要求无意义凑字数。
- QA 多选场景须保留题目选项、区分选项结论与自由解释；原始题目、选择标签和验证准则全部记录。

两个格式分别固定 `max_new_tokens`（例如 A=64，B=160；采用前须核实现有 generate 与 evaluator 的停止方式）；同一格式三臂一致。保留实际 AR 生成长度、轮次数、EOS 与最后一轮截断。**不能仅挑回答比较长的样本作为主结果**；长度分组只是预先声明的辅助分析（如 AR 生成长度 ≤8、9–32、>32 tokens），所有样本仍进入主表。

处理原始视频时，复用项目稳定的 processor 与采帧方法（通常抽样 16 帧，但必须从实际代码核实），保存**原始视频的采样帧号和真实时间戳**，不要把缓存 MP4 的 0.53 秒封装时长当成真实片长。相同输入内容、顺序、processor 配置和 feature path 必须生成一致的 target context。不同 prompt/格式必须有隔离缓存 key；不允许复用旧 caption prompt 的融合特征或把相同 video-only cache 误用为相同完整输入。

## 3. 执行流程：三道门禁

### Stage 0：纯审计与数据小样本准备

输出数据 availability 表（数据集、官方来源、split、视频/QA 数、许可、视频是否实际可读、音视频与帧率、标签格式、下载量、需要的转换）。建立统一 QA manifest：`dataset, split, video_id, source_id, question_id, question, options(if any), gold_answer, question_type, video_duration, sample_frame_ids/timestamps, sample_seed, hash, prompt_mode`。

统一评测器必须能覆盖开放式短答与多选 QA；使用原项目中经验证的推理入口，仅写新 adapter 或独立评测入口。开发自检至少验证：题目不泄漏答案、同源检测、分层抽样、缓存键隔离、实际输出长度、逐 token AR 比较、n 视频聚合、对应统计和单位测试。

### Stage 1：小型 GPU smoke 门禁

每个可用数据集先挑冻结名单前 **3–5 条视频**、每条最多 2 QA，两种格式均测；先做 C0，再 C1/C2。检查：
- target 独立 greedy AR 与三个 SPEC 输出**逐 token 一致**，且三臂输出相同；这条门禁不可用 logit 容差替代。
- 实际视频像素/帧输入/processor、cached 特征路径、prompt、选项和 target 的 AR context 一致；只允许 checkpoint 不同。
- 树预算/root/bonus/EOS 统计一致，解码指标与现有实现口径相同。
- 短答案造成“只有一轮或极少 draft token”的频率是否过高；这类样本标为 `speed_informative=false`，**保留在原始主样本和准确率表中**，但不给出夸大的 speedup。
- 如果缺数据/输入不一致/无损失败/持续 OOM，保存失败 trace 并停在该数据集门禁，不跳过失败样本以挑有利结果。

### Stage 2：完成三模型固定样本评测（不训练）

门禁通过后，按冻结 manifest 完成每个数据集两种格式的 C0/C1/C2；重用同一 target AR 输出、输入配置和问题 ID。所有运行使用同一空闲 GPU 与数值路径，保留每条 GPU 环境、实际调用数量及失败情况。不得占用其他人的任务或无期限后台等待；不修改共享依赖，不覆盖旧缓存、checkpoint 和结果；输出到独立 `results/videoqa_transfer/<run_id>/` 目录。

预先规定唯一主比较：**`C2−C1` 在每个数据集和格式上的 mean per-video τ**；同时报告 `C2−C0`、`C1−C0`。本轮还有一个更重要的解释变量：**target AR 生成长度与目标预测不确定性**，必须保留每样本/每视频数据以解释为什么某任务看起来容易或困难。

正式数据均保留：
- 每条 question 的 AR tokens、生成 token 数、实际验证轮次、mean/pooled τ（口径分开）、accepted draft token 与 terminal clipping（root/bonus 的单独计数）、可用的 top-8 候选覆盖、首拒位置、target entropy / top1-top2 margin；不要求每条完整保存全词表 logits，可流式汇总。
- 视频级 paired comparison：C2−C1 / C2−C0 / C1−C0 各自变化、正/负/不变视频数量、按视频重采样的 bootstrap 95% CI（例如 2000 次，seed 20261013）；至少输出每视频的 paired 原始值，不能把 token 或同一视频多个问题当作独立样本。
- QA 任务表现：使用对应数据集的官方指标（有条件就计算），另记录可解释的规范化答案匹配 / 多选正确率；**不要把不同的自由文本表述用未经核准的简单完全匹配当成唯一语义正确性标准**。因为同一 target 与 greedy 解码输出必须一致，C0/C1/C2 不应出现答案质量差异；若出现，优先按无损 bug 排查。
- 实际性能：在相同硬件、负载、warmup、计时窗口的可比条件下，独立测 decode-only latency / ms-token、tree build、draft、target verification 耗时；若日志 trace 重、不同日负载不同，则只给 τ，不据此宣称速度收益。可测时另报含 prefill/视频处理的端到端结果。

### Stage 3：解释差异，而不是只输出排行榜

对每个数据集/Format 生成同一张对比表：
`dataset | format | n_videos | n_QA | AR_length_mean/median | fraction_short/one_round | τ_C0 | τ_C1 | τ_C2 | Δ(C2−C1) [video bootstrap CI] | Δ(C2−C0) [CI] | top8_cover | target_entropy | decode_ms/token | SPEC=AR`。

分开回答：
1. 简单问答是不是**整体**让三臂都更容易预测？
2. 在相同问题/视频上，C2 是否**相对于 C1**更强？这是跨任务 checkpoint 结果，不是公平训练下的 OPD 因果证明。
3. 观测差异是否可由生成长度/一轮完成/target entropy/问题类型/训练源域差异解释？不能仅凭总体 τ 猜测“视频难度”。
4. Format B 是否真的增加了有意义的连续解码轮次，并保持合理的视频依据？不能仅靠拉长回答获取虚假加速优势。
5. 三个数据集的难度趋势是否一致？若不一致，展示逐视频反例而不是汇总平均掩盖。
6. 早期图像 OPD>SFT 的说法，经历史日志审计，支持程度是什么？区分“图像上 GLANCE 比其他方法好”与“OPD loss 因果优于 SFT”。

## 4. 统计、结论和后续决策

本轮约 20–30 视频/数据集只属于**探索性开发集筛查**，不得宣传“已证明全数据集 OPD 泛化有效”。不要用多次看结果后改 seed、改样本数、筛数据集和格式寻找显著性；如果有多个数据集和格式，显示完整结果，标记多重探索性比较，不把任何一个最有利子集自动升为确认性主要结论。

最后按以下决策报告**最值得做的一个下一步**，不要自动启动：

- **情况 A：** QA 简单任务中 C0/C1/C2 的 τ 全上升，但 C2−C1 仍近零 → 任务变简单有利于 speculative decoding，但没有 OPD 独特优势；不要拿这个结果发表“OPD 有效”。
- **情况 B：** 至少一个 QA 数据集出现稳定、可重复的 C2−C1 正差异、且产生实测接受长度/速度收益 → 优先做该类型任务的**同起点、同训练视频、同监督/teacher 计算预算**的领域内 SFT vs OPD 小型训练对照；本轮不能直接认定 OPD 机制获证。
- **情况 C：** Format A 答案过短、均在一轮完成 → 这类 QA 只适合预测准确性与候选覆盖，正式速度实验转向 Format B 或自然较长答案，而不是继续增加简答数据量。
- **情况 D：** 目前三臂的跨任务迁移都差 → 先确认 prompt/video 预处理与分布匹配；若需训练，后续必须做同数据配平，不能把现有 C2 的失败归罪于 OPD 本身。
- **情况 E：** 跨数据集差异主要随 entropy/问题类型变化 → 将“什么任务条件下 OPD 的候选边界能改善”明确为可检验的下一轮研究问题，暂不发明新 loss。
